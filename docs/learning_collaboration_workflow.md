# 学习型开发协作流程

最后更新：2026-06-21

本文档用于约定本项目后续“边开发边学习”的协作方式。目标不是由 Agent 一次性包办所有实现，而是让开发者在真实项目中通过小切片、手动验证、单元测试和纠错复盘逐步理解工程实践。

---

## 1. 协作目标

本项目后续默认采用“学习者先尝试 + Agent 指导纠错”的开发方式。

核心目标：

1. 每次只推进一个清晰的小切片。
2. 每个切片都说明要学习的概念。
3. 修改前先给出方向、边界和验证方式。
4. 优先由开发者自己运行命令、观察结果、记录问题。
5. Agent 根据实际结果解释原因、定位问题、给出修正建议。
6. 功能完成后补充测试、验证结果和开发日志。

---

## 2. 默认分工

### 2.1 开发者负责

- 按指导阅读相关文件。
- 尝试修改小范围代码。
- 手动运行验证命令。
- 贴出报错、测试结果或不理解的问题。
- 在理解后确认是否继续下一步。

### 2.2 Agent 负责

- 说明本阶段目标和学习重点。
- 指出应该先看哪些文件、改哪些文件。
- 给出最小验证命令和预期结果。
- 根据报错或测试结果定位原因。
- 解释相关语言、框架、架构概念。
- 在开发者要求时再进行代码修改。
- 阶段结束时协助整理开发日志。

---

## 3. 标准切片流程

每个开发切片按以下顺序推进：

```txt
确认目标
  ↓
解释概念
  ↓
指定阅读文件
  ↓
给出尝试任务
  ↓
开发者手动修改或运行命令
  ↓
根据结果纠错
  ↓
补充测试或验证
  ↓
记录开发日志
  ↓
给出下一步建议
```

如果开发者明确要求“你来实现”，可以临时切换为 Agent 主动实现模式，但仍然需要保持小步验证和日志回填。

---

## 4. 验证原则

后续验证必须继续遵守：

```txt
.clinerules/terminal-timeout-and-small-step-validation.md
```

基本原则：

1. 不把多个耗时命令串成一条长命令。
2. 每条命令只验证一个目标。
3. 命令失败后先分析原因，不继续叠加后续命令。
4. 后端优先使用 `pytest` 验证。
5. 前端优先使用 `pnpm -C frontend typecheck` 验证。
6. C++ Core 优先使用最小 CLI / JSON 输入输出验证。
7. 能写单元测试的小切片，默认补充或更新单元测试。

---

## 5. 日志要求

每个小阶段完成后，在对应成员日志顶部追加记录。

日志不仅记录“完成了什么”，也记录：

- 为什么这样做。
- 中间遇到了什么错误。
- 错误是如何定位的。
- 学到了什么概念。
- 还有什么没理解。

推荐模板：

```md
## YYYY-MM-DD HH:mm - 阶段名称

### 本阶段目标

### 学习目标

### 你先尝试的内容

### 修改文件

### 执行命令

### 验证结果

### 遇到的问题

### 纠错与解释

### 学到的东西

### 仍然不理解的问题

### 下一步建议
```

---

## 6. 对话恢复方式

新对话恢复任务时，优先读取：

```txt
1. docs/development_logs/README.md
2. docs/learning_collaboration_workflow.md
3. docs/development_logs/member_a_fastapi_react.md 或 docs/development_logs/member_b_cpp_godot.md
4. docs/current_development_plan.md
5. docs/api_contract.md
6. .clinerules/terminal-timeout-and-small-step-validation.md
```

恢复后先确认：

1. 当前正在做哪个成员范围。
2. 上一个阶段验证是否通过。
3. 下一步是学习指导、开发者尝试，还是 Agent 主动实现。
